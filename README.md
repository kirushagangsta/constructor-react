# Конструктор страниц — React

Визуальный редактор страниц: дерево блоков, правка стилей по контрольным точкам,
отмена и возврат с человекочитаемым журналом правок.

## Зачем этот репозиторий

Это вторая реализация одного и того же редактора. Первая —
[constructor-site](https://github.com/kirushagangsta/constructor-site) на Nuxt 4 и Vue 3.

Доменный слой здесь взят из неё **без изменений** — файлы в `entities/page/lib`
перенесены как есть, правились только пути импортов. Переписан слой представления.
Смысл ровно в этом: проверить на практике, что логика редактора действительно
не зависит от фреймворка, а не только считается таковой.

## Архитектура

Feature-Sliced Design. Папки первого уровня — слои, внутри слоя — слайсы,
внутри слайса — сегменты (`ui`, `model`, `lib`, `config`).

```
src/
├── app/                        композиция приложения и глобальные стили
├── pages/editor/               страница редактора: расставляет виджеты
├── widgets/                    самостоятельные куски интерфейса
│   ├── editor-toolbar/         верхняя панель
│   ├── structure-panel/        дерево блоков и журнал
│   ├── editor-canvas/          холст
│   └── inspector-panel/        свойства выделенного
├── features/                   пользовательские сценарии
│   ├── block-editing/          создать, дублировать, удалить, перенести
│   ├── node-properties/        правка текста и стилей
│   ├── page-history/           отмена, возврат, журнал
│   └── breakpoint-switching/   выбор ширины экрана
├── entities/page/              страница как сущность — ядро проекта
│   ├── model/                  types, store (редьюсер), selectors, context
│   ├── lib/                    чистая логика дерева, перенесена из Vue-версии
│   ├── config/                 контрольные точки, сброс стилей готовой страницы
│   └── ui/                     NodeView, BlockTree
└── shared/                     ничего не знает о домене
    ├── ui/                     Button, Field
    └── config/                 voidTags
```

Единственное правило: слой импортирует только то, что ниже него. Снаружи слайс
виден через свой `index.ts` — внутренняя раскладка остаётся его делом.

### Решения, которые стоит заметить

**`breakpoints` и `pageReset` лежат в `entities/page/config`, а не в `shared`.**
Это выглядит как общие константы, но `breakpoints` типизирован `StyleVariant` —
доменным типом. Положить их в `shared` значило бы заставить нижний слой знать
о сущности, то есть развернуть зависимость вверх. В `shared/config` остался
только `voidTags`: перечень пустых HTML-тегов — знание о вёрстке, а не о домене.

**Провайдер состояния живёт в `entities/page/model`, а не в `app/providers`.**
Хранилище нужно фичам и виджетам. Если провайдер объявлен в `app`, то `useEditor`
импортируется из верхнего слоя — ровно то, что FSD запрещает. Сущность владеет
состоянием, `app` его только монтирует.

**Фич четыре, а не по одной на кнопку.** Слой `features` описывает сценарии,
а не элементы управления. «Перенести блок выше» и «перенести наружу» — один
сценарий работы с составом страницы, поэтому они в `block-editing` вместе
с созданием и удалением. Дробить их до слайса на кнопку значило бы получить
семь папок по десять строк и пустую церемонию вместо структуры.

**Виджеты не содержат логики.** `editor-toolbar` — это композиция фич и больше
ничего. Логика живёт в фичах и в сущности, виджет отвечает только за раскладку.

### Чем это отличается от Vue-версии

Во Vue-версии структура традиционная для Nuxt: `components/Ui` для примитивов,
`components/Constructor/*` по узлам интерфейса, `composables`, `utils/constructor`,
`constants`, `types`. Разделение по типу файла, а не по смыслу.

Здесь то же содержимое разложено по смыслу: `utils/constructor` стал
`entities/page/lib`, `components/Ui` — `shared/ui`, `components/Constructor/Toolbar`
разошёлся по фичам, которые эти кнопки выполняют. Ядро при этом не изменилось
ни на строчку — что и было проверкой.

## Решения в коде

**Тег — это данные, а не компонент.** `NodeView` рисует узел через
`createElement(node.tag)`, поэтому новый тег не требует ни нового компонента,
ни ветки в `switch`.

**Стили хранятся как данные и собираются в css.** Блок не носит инлайновый
`style` — у него есть набор объявлений по контрольным точкам, из которых
`buildEditorCss` собирает таблицу стилей. На холсте медиазапросы не годятся:
они смотрят на ширину окна, а не холста, — поэтому стили нужной ширины
вычисляются заранее.

**Журнал не знает о кнопках.** Название шага не пишется в обработчике,
а выводится из разницы между страницей до и после (`describeChange`). Любая
новая правка попадает в журнал сама, без отдельной строчки кода под неё.

**Правка идёт по копии.** Утилиты ядра меняют дерево на месте (`moveNode` режет
`children`), а React не должен видеть один и тот же объект «до» и «после» —
иначе нечего сравнивать и нечего перерисовывать. Поэтому `structuredClone`
перед каждым изменением.

**Подряд идущие правки склеиваются.** Набор текста — это вызов редьюсера
на каждую букву. Без склейки журнал распухал бы до шага на букву, а отмена
откатывала бы по одной. Метка `mergeKey` держит такие правки одним шагом,
а смена блока, ширины или отмена её сбрасывают.

**Перевод номеров живёт в одном месте.** Человек видит номер блока с единицы,
`moveNode` считает места с нуля. Перевод вынесен в `placementOf`, чтобы
не повторять арифметику в каждой кнопке переноса.

## Запуск

```
npm install
npm run dev     # редактор на http://localhost:5173
npm test        # 39 тестов
npm run build
```

## Тесты

39 штук, Vitest и Testing Library на happy-dom. Разложены по той же структуре,
что и код.

- `tests/entities/page/store.spec.ts` — редьюсер: правки, запреты, журнал,
  отмена, склейка шагов.
- `tests/entities/page/selectors.spec.ts` — выборки по дереву и перевод номеров.
- `tests/app/editor.spec.tsx` — редактор целиком через интерфейс: выделение
  кликом по холсту, правка текста и стиля, перенос блока, выключённые кнопки,
  вычеркнутый шаг после отмены.
